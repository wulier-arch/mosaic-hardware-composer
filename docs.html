01 / Overview

项目概述与设计语言

MOSAIC 拼造 是一个在线硬件定制平台。用户从结构化的模块库中挑选开发板、传感器、电机、电源、 通信与结构件，平台在每一次加购时实时校验这套组合在物理与电气层面是否可行，最终输出可下单的方案清单。

要解决的问题

  • 买错。3.3V 主控接 5V 传感器、IO 数量不够、I2C 地址撞车——这些错误通常在收到货、开始接线时才暴露。
  • 返工。工程师要手工核对引脚分配、总线占用与功耗预算，一轮打样前要花两三天做纸面推演。
  • 断链。选型、下单、付款、发货分散在不同工具里，方案无法复用，批量采购没有流程。

视觉设计语言

设计系统融合了两处参考：ArtCraft（getartcraft.com）的暖白纸感底色、近黑墨色、发丝分割线与编号章节排版； WuXiaoMuer 的 GitHub 主页的紫罗兰主色、圆角发光与极客徽章气质。合成后的观感是「工程编辑体」—— 像一本排版克制、信息密度高的技术手册。

06 / Responsive

响应式设计要求

断点采用「内容优先」而非设备优先的原则：一旦布局开始拥挤就换断点，不绑定具体机型。

断点目标环境布局变化
≥ 1280px桌面宽屏 工作台三栏（290 / 自适应 / 350）；模块网格每行 4 列；筛选侧栏常驻左侧。
1080 – 1280px桌面窄屏 / 小笔记本 工作台三栏收窄为 250 / 自适应 / 320；模块网格 3 列；筛选侧栏收为可折叠。
860 – 1080px平板横屏 工作台改为顶部三页签（选模块 / 我的方案 / 校验汇总）；详情页双栏改为单栏；首页热度区改单列。
620 – 860px平板竖屏 / 大屏手机 导航折叠为汉堡菜单，链接纵向展开；表单双列改单列；卡片网格 2 列；Toast 改为通栏贴底。
< 620px手机 模块网格 1 列且隐藏简介、缩小缩略图；步骤条隐藏文字标签只留圆点；统计卡改单列；页脚改单列；弹层宽度 94vw。

强制要求

  • 触控目标。所有可点击元素的命中区域不小于 40×40px，移动端导航项纵向内边距 11px。
  • 横向滚动。表格类内容（订单表、规格表）统一包裹在可横向滚动的容器中，页面本身不产生横向滚动。
  • 粘性元素。工作台与结算页的汇总栏使用 position: sticky，但移动端必须解除粘性并改为文档流，避免遮挡内容。
  • 图片与图表。所有 SVG 使用 viewBox 与百分比宽度自适应；流程图设置最小宽度并允许容器横向滚动，不缩放变形。
  • 动效降级。遵循 prefers-reduced-motion，在该媒体查询下把所有动画与过渡时长压到 0.001ms。
  • 打印。导航、页脚、操作按钮统一带 no-print，配货单与说明书可直接打印或导出 PDF。
07 / Engine

兼容性校验规则

引擎在每次方案变更时全量重算，输出「通过 / 提醒 / 冲突」三级结论。规则实现位于 assets/js/core.js 的 Compat.evaluate()。

编号规则级别判定逻辑与处置建议
R0缺少主控冲突 方案中没有主控开发板时阻断结算。主控是全部兼容性判断的基准，没有它无法计算总线与供电上限。
R1接口数量超限冲突 逐项比对 UART / I2S / CSI / ADC / PWM 的占用数与主控提供的路数；SPI 按「每个控制器最多 3 个从设备」折算。
R2GPIO 引脚不足冲突 累加所有模块占用的 IO 数并与主控可用 IO 比较。建议加装 PCF8574 扩展 8 路，或改用 I2C 接口的模块。
R3逻辑电平不匹配提醒 3.3V 主控搭配 5V 器件时告警；若方案含「4 路双向电平转换」则降级为通过，并提示通道数是否够用。
R4I2C 地址冲突提醒 按地址分组，同一地址出现两个及以上器件即告警。方案含 TCA9548A 时降级为通过，并提示需在代码中切换通道。
R5供电能力不足冲突 按峰值电流汇总 5V 与 3.3V 轨负载，与主控供电能力加外部电源输出之和比较。余量低于 25% 时降级为提醒。
R6算力档位不足冲突 取全部外设所需的最高算力档（基础 / 进阶 / AI）与主控档位比较。摄像头与神经网络推理类模块要求 AI 档。
R7缺少必需的总线协议冲突 校验 WiFi / BLE / CAN 等协议能力。CAN 收发模块要求主控内置 CAN 控制器，只有 STM32 系列满足。
R8缺少驱动板或外接电源提醒 含执行器但无任何电机/舵机驱动板时告警；需要 12V / 独立 5V 的器件找不到对应电源时告警。

难度与工时估算

难度基准 1 分，模块种类超过 2 类 +1、超过 6 类 +1，含驱动板 +1，含焊接或定制 PCB +1， 含 12V 强电走线 +1，含 AI 档模块 +1，上限 5 分。装配工时 = 0.5 小时基础 + 每类模块 0.28 小时 + 驱动板 0.6 小时 + 焊接 1.6 小时。

08 / Heat

选型热度模块（示意）

数据性质声明：本模块为演示数据。热度指数由「平台需求分布基线」与「本机真实选型行为」加权合成， 用于验证排序、筛选与图表链路，不代表真实市场数据。

本次修复与补全的内容

  1. 补全时间维度。原实现只有单一热度值。现提供「近 7 日」与「近 30 日」双口径切换， 7 日口径读取种子环比，30 日口径由 (d7 − d30) / d30 反算环比，保证三个数字互相自洽。
  2. 修复数据不自洽。此前热度值、环比、排名可能彼此矛盾。现在 d30 由 d7 与 delta 反推得出（d30 = d7 / (1 + delta)），三者从构造上就不可能冲突。
  3. 接入真实行为。新增 Heat.record(type, id) 埋点，记录浏览 / 加购 / 下单三类事件到 localStorage； 综合热度 = clamp(基线 × 0.7 + 本机加权 × 0.3, 0, 100)。无本机数据时自动回退为纯基线，不产生偏差。
  4. 补全可视化。新增热度条、环比涨跌箭头（遵循中国市场惯例：涨为红、 跌为绿）、14 日迷你趋势线（种子可复现，末端收敛到当前值）、分类热度均值聚合。
  5. 补全交互。时间范围切换、分类筛选、点击跳转详情、分类行点击反向筛选、清空本机行为数据后自动重算。
  6. 明确口径。页面常驻数据口径说明卡片，后台「热度与埋点」页提供埋点明细审计与清空入口。

09 / Commerce

下单、付款与后台处理流程

订单状态机

状态名称可执行动作触发方

端到端链路（已在演示环境打通）

  1. 结算页读取工作台方案，展示模块清单与实时计费；校验收货人、手机号（/^1[3-9]\d{9}$/）、 省份、详细地址（≥5 字符）、可选邮箱格式、发票必填项与条款勾选。
  2. 提交订单前二次校验库存，随后写入订单对象并生成订单号 MS + 时间戳 + 3 位随机， 跳转到支付页。
  3. 支付页按渠道生成支付凭据（code_url / qr_code 占位）与支付单号， 渲染二维码、启动 30 分钟倒计时，并每秒核对一次订单状态。
  4. 支付完成由「模拟回调」按钮触发，或由真实服务端异步通知触发。回调落库时执行三件事： 写入支付渠道与支付单号、记录回调来源用于审计、原子扣减库存。
  5. 后台实时可见该订单，可执行「开始备货 → 发货（必填快递单号）→ 标记完成」， 也可在已付款或备货中状态发起退款；退款时自动回滚库存。
  6. 前台订单页展示完整状态时间线、物流单号与配货清单，支持确认收货与一键复购。

演示环境的数据存放在本机 localStorage（键名 mosaic.orders.v1）， 前台与后台共享同一份数据，因此下单后无需任何操作即可在后台看到订单。 生产环境只需把 Store 的读写替换为服务端接口调用，其余业务逻辑不变。

10 / Payment

微信支付与支付宝接入方案

支付能力已按「前端只负责渲染与轮询、签名与验签全部在服务端」的原则预留。项目内置可直接部署到 Vercel / Cloudflare Workers 的 Serverless 示例。

目录结构

api/
├── pay/wechat/create.js   # V3 Native 下单，返回 code_url
├── pay/wechat/notify.js   # 异步通知验签 + 解密 + 置为已付款
├── pay/alipay/create.js   # alipay.trade.precreate，返回 qr_code
├── pay/alipay/notify.js   # notify_url 验签（RSA2）+ 置为已付款
└── orders/index.js        # 订单创建与状态查询（服务端权威数据源）

前端对接点

只有两处需要改动，都在 assets/js/core.js 的 Pay 对象内：

// ① 下单：把本地生成改为请求服务端
Pay.create = async (order, channel) => {
  const r = await fetch(`/api/pay/${channel}/create`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ orderNo: order.no, amount: order.amount, subject: order.schemeName })
  });
  const d = await r.json();
  return { channel, code: d.codeUrl || d.qrCode, payNo: d.prepayId, expireAt: d.expireAt };
};

// ② 查询：由服务端返回权威状态，前端仅做展示
Pay.query = async (orderId) =>
  fetch(`/api/orders/${orderId}/status`).then(r => r.json());

安全红线：商户私钥、APIv3 密钥、支付宝应用私钥等敏感凭据只能存放在服务端环境变量中， 绝不能出现在前端代码或静态托管产物里。回调接口必须验签并校验金额，防止伪造通知。

11 / Deploy

部署方案

站点为纯静态产物，无构建步骤、无运行时依赖。所有资源路径均为相对路径，可直接托管在任意静态服务上。

平台配置方式已提供文件
GitHub Pages仓库 Settings → Pages → Source 选择 GitHub Actions，推送到 main 即自动发布 .github/workflows/deploy-pages.yml、.nojekyll
Vercel导入仓库后零配置识别为静态站点；api/ 目录自动转为 Serverless Functions vercel.json
Cloudflare Pages连接仓库，Build command 留空，Output directory 填 / _headers、_redirects

本地预览

# 任选其一，必须通过 HTTP 服务访问（不要直接双击打开 HTML）
python3 -m http.server 8080
npx serve .
vercel dev

部署后需要确认的项

  • 若部署在子路径（如 user.github.io/repo/），页面间的相对链接会自动正确解析，无需改配置。
  • 后台口令与演示数据均存于浏览器本地，换设备后数据不共享——这是演示环境的预期行为。
  • 接入真实支付后，需在 vercel.json 或 Worker 配置中把 /api/* 路由到服务端函数。

后续迭代建议

  • 真实后端。引入云数据库与用户认证，把方案、订单、库存迁到服务端；订单创建与库存扣减放进同一事务。
  • 引脚级自动分配。在现有总线数量校验之上，进一步做具体引脚编号的自动分配与冲突消解，输出接线表。
  • 固件模板。按方案组合自动生成 PlatformIO / Arduino 工程骨架与驱动初始化代码，随单交付。
  • 3D 装配预览。基于模块尺寸与接口朝向生成爆炸图，下单前预览物理干涉。
  • 供应链。对接元器件库存与价格接口，实现缺货自动替代与实时报价。
  • BOM 版本管理。方案支持多版本对比与变更记录，适配硬件产品的迭代节奏。
